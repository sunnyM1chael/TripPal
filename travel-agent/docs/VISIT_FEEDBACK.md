# 去过之后：实现与 Review

## 用户路径

我的行程 → 按顺序标记已完成站点 → 展开“去过了，记一下体验” → 填写评分、实际体验，以及可选实际花费、花费口径、排队和再访意愿 → 保存体验与私有草稿。

刷新可恢复，保存后可编辑草稿。修改体验后希望重新组织正文，应清空草稿正文再保存。草稿使用确定性模板整理用户事实，不调用模型润色；驴友可在对话中帮忙改写，用户再自行核对填入。

登录账号可打开已保存草稿到现有博客发布页。页面重新通过鉴权读取草稿，只在 URL 携带行程和站点 ID，不传递正文或 token。用户继续选择真实平台商家、上传自己的照片并点击发布，才调用原 Java 创建博客接口。高德地点未关联平台商家时不能自动发布；公园等无平台商家的地点可保留私人记录。

长期人均预算使用独立确认按钮和现有偏好接口；填写实际花费不修改偏好。游客可保存私人反馈，账号登录不会自动转移游客记录。

## 数据与接口

`PUT /api/v1/itineraries/{id}/stops/{stop_id}/feedback`

必填 `expected_revision`、`rating`（1–5整数）、`experience`（1–1500字）；可选 `actual_cost_yuan`（最多两位小数）、`cost_scope`（person/party）、`queue_minutes`、`would_return`、`draft_title`、`draft_content`。可选数值未知为 null，零和 false 保留。

反馈覆盖保存在所属站点的 `feedback` 字段中，包括 `source=user_reported`、更新时间、`draft.status=private_draft`。复用行程 JSON，不新增 SQL 表；需现有行程、通知表已经初始化。SQLite/MySQL 使用同一行程存储接口。本功能不把反馈写入公共评分，不验证物理到店，不自动纳入公共 RAG。

## 按这个顺序读代码

1. `app/itineraries/feedback.py`：输入约束；只整理用户提供的数据；先按 owner 读取，再检查版本和完成状态；最终由 store.update 的 SQL 版本条件防止并发覆盖。
2. `app/api/itinerary_routes.py`：复用服务端鉴权和限流，owner 不接受前端输入。
3. `src/components/VisitFeedbackForm.vue`：保存结果才提示成功；冲突后读取最新版本并保留输入供用户核对；账号变化后丢弃旧响应。
4. `src/views/blog/BlogEdit.vue` 与 `src/utils/visitFeedback.js`：重新读取本人草稿，核对平台商家；公开前将草稿纯文本转义为兼容原博客展示的 HTML，检查编码后的正文不超过原表 2048 字符限制。
5. `app/itineraries/tools.py` 和 `app/tools/travel.py`：新增 get_visit_feedback，只读取本人当前行程记录；保存与发布仍由页面操作。visit-review Skill 指导回顾、编辑、偏好确认和发布步骤。

## 验证

自动化覆盖：未完成站点拒绝、跨 owner 拒绝、无效金额/评分/伪造字段、未知与零的区分、版本冲突、并发仅一次成功、存储重新打开恢复、编辑行程保留反馈、清除记忆删除反馈、工具读取隔离和发布文本转义。

2026-10-22 本次验证：反馈、行程与 Skill 相关 Python 测试共 63 项通过；Node 草稿转义测试 1 项通过；涉及文件 ESLint、Python 编译及完整 Vite 生产构建通过。测试启动时遇到执行环境的 SOCKS 代理缺少 socksio，测试进程设置 NO_PROXY=* 后完成纯本地验证；未修改应用代理配置或 .env。

人工验收：在已启动的项目创建并完成一站，填写与保存，刷新，修改草稿，打开发布页核对商家与照片；分别检查偏好保存与发布结果。真实 MySQL、浏览器和 Java 发布联调应独立记录验收结果，单元测试不代表已经通过这些检查。不要为了验收直接发布虚构点评。

## 当前边界

每个站点保存一份可覆盖反馈；删除行程或清除旅行记忆会一并删除私人反馈和草稿，已经公开的博客仍由 Java 博客业务独立管理。发布页后续修改不回写私人草稿，重复点击发布的幂等机制沿用原有业务。未来如需独立反馈列表、多次到访、审核、检索索引或发布状态跟踪，再拆分独立实体。
