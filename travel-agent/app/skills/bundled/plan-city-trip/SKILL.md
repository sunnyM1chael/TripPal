# 多日行程规划

## 明确需求

1. 提取城市、天数、同行人数、预算及口径、兴趣与节奏、步行/驾车方式。优先使用本轮输入，偏好记忆只作补充。每轮只问最影响安排的一至两个缺项，不重复问已给信息。
2. 将预算确认并换算为“全体同行人的全程总预算”：人均总额乘人数；人均每天金额再乘天数。预算包含哪些项目也需说明，不能把餐费预算当完整旅行预算。
3. 询问出发日期及每天可用时段；日期未知可用第1天、第2天，不猜日期。每天时段相同时才使用共同 start_time/end_time；未给时段可先提出09:00至18:00的建议并明确是假设，用户不接受就调整。首末日抵离时间不同应另行提示，不能声称已核算赶车时间。
4. 当前支持一个城市、1至7天，多日每天最多4个真实地点。跨城或更长旅行先拆分城市和阶段，说明当前范围。不把“少走路”理解为同意驾车，不虚构公交/地铁班次。

## 查询并分天

5. 城市含糊时 search_cities 消歧。使用 search_trip_places，以用户兴趣和同城区域为关键词批量查询候选；未提供批量工具时分次使用 search_city_places。只使用查询实际返回的 poi_id，城市同名、同名分店或车站需核对地址。
6. 按区域邻近和体验搭配分天，每天通常2至3个主要点，含用餐最多4站；亲子和慢游减少站点、增加停留和休息。先按真实地址分组，不声称这是最优路径。候选不足时补查或说明不足，不以重复地点凑天数。
7. 使用用户接受的 walking 或 driving。建议游览60至120分钟、用餐45至90分钟、每日额外休息20至40分钟，明确这些是建议。仅填用户实际声明的 preferences，不生成用户未表达的忌口或家庭成员属性。
   需要平台优惠券或平台餐费核查时，再用 search_shops、shop_detail、compare_shops 查询 Java 业务库；核对名称和地址，不把高德 poi_id 强行映射成 shop_id。
8. 酒店接驳、每天首站前交通和末站返程不在当前路线计算内。起点未确定时列为待补充，不将当前位置或酒店坐标默认为已知。遇到必须包含接送、跨城、预约的要求先解释范围并单独核实。

## 生成与核验

9. 生成可编辑方案时调用 create_itinerary：填 day_count、可选 start_date、people、全程 budget_yuan、mode、共同每日时段、每日 rest_minutes 和 preferences；stops 按天和游览顺序排列，每站标 day、poi_id、stay_minutes、kind。各天从1连续编号，每天至少一站；同一天不重复地点。
10. 服务端会重新读取地点详情、核对城市，并对每天相邻站点调用高德，不跨夜串路线。不要再为同一批站点逐段重复调用 plan_route。需要比较候选路线时，可先少量调用 plan_route，再决定站点顺序。
11. 检查返回的 summary.days：逐天看 within_time、time_estimate_complete、实际路线与费用。某天超时就减少站点或停留；用 get_current_itinerary 读取最新版本，再 edit_current_itinerary 调整，不能擅自延长用户的可用时间或改交通方式。上移/下移只限当天；不能删空一天，也不能修改已完成站点。
12. 高德失败时将该段距离、耗时及后续钟点标为未知，不能当0或凭直线距离代替。可保留带缺口的草案并明确提示刷新，不能称“路线已全部验证”。没有行程保存工具时只给文字建议，说明未核算和未保存；用户明确只要文字建议时不要保存。

## 输出

13. 先给城市、天数、人数、交通方式、总预算口径与规划假设。逐天列出日期/天序、地点及地址、建议停留、查询到的相邻路线耗时与距离、当天已知时长和时间冲突。
14. 给出全程已知参考消费小计、未知价格点数，以及住宿、交通、门票、预约和营业信息等待确认项。高德参考消费不是票价或实时套餐报价；有未知费用时不能保证预算够用，也不默认优惠券可抵扣。
15. 只有 create_itinerary 成功才说已保存，指向“我的行程”；记录原有单日兼容性。提供一条有用的调整建议，不堆砌长篇景点介绍。

例：用户说“常州3天、两个人、全程总预算1500，喜欢园林和小吃，不想太累，驾车”。先补每天时段与日期，再查同城候选、按区域分3天，服务端核算各天站点间路线。1500不能再乘人数；住宿与门票未核实就明确未知。

验收：不猜地点ID；天序完整；按天算路线和时间；预算口径正确；失败与未知项可见；保存及调整由工具结果证明。
