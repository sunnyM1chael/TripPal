# 驴友：优惠券候补执行闭环

本流程复用现有 Java 接口，不新增 Java 表、SQL 或中间件配置。重启 Python，刷新 Vue 即可加载新代码。

## 使用方式

登录后对驴友说：“查一下小店的优惠券，帮我准备候补订阅。”把“小店”换成平台数据库中的商户名称；高德地点不能作为平台商户使用。

1. 驴友查询商户和优惠券，准备操作卡。此时尚未写入 Java。
2. 页面展示商户、具体券、购买价、面值、规则、有效期和现有候补状态。
3. 加入候补前，用户勾选知情说明，再点击“确认加入候补”。
4. Python 核验登录归属，重新查询券的价格、规则、状态和有效期；变化时拒绝旧卡，要求重新准备。
5. 调用 Java `/voucher/subscribe`，再调用 `/voucher/get/subscribe/status` 回查。
6. 页面显示带查询时间的 Java 状态。点击“查询当前状态”可再次核实；候补队列中可“准备退出候补”，核对并确认后调用 `/voucher/unsubscribe` 并回查。

**候补不是普通提醒。** 现有 Java 逻辑在补库存/退券后可能自动发券并创建券订单。状态 `0` 为未订阅，`1` 为候补队列中，`2` 为已发券并创建订单。取消候补不会取消已有订单。本流程不调用购买、支付、秒杀下单或订单取消接口。

## 工程实现

- 模型仅有 `prepare_voucher_subscription` 和 `get_voucher_subscription` 两个工具，没有确认/执行工具；MCP 继续保持原有只读白名单。
- 前端显式确认走 `POST /api/v1/voucher-subscriptions/{action_id}/confirm`，不能用模型返回的任意 URL 执行操作。
- 当前登录令牌只在 Python → Java 请求中透传，不进入模型上下文、操作卡或日志。客户端不能传入用户 ID。
- 待确认卡绑定已核验的用户、商户、券、操作类型和原始规则；5分钟有效。普通券、下架券、过期券、缺失价格/失效时间的券不能加入候补。
- 同一操作卡并发确认只发送一次写入。写入失败/超时不自动重试；重复确认只能回查。Java 回查失败明确显示“操作结果尚未确认”。
- 回执表示查询时状态，不承诺最终有券或成功获券；再次查询以 Java 当前状态为准。
- 操作卡存于当前 Python 进程，最多2000张，重启失效；Java 订阅状态仍由 Java/Redis 管理，不依赖 Python 操作卡。当前使用单进程启动；多 worker/多实例部署需先把待确认状态与锁移到共享存储。

## 验收

自动化测试使用模拟 Java HTTP 接口，覆盖聊天查询 → 准备卡 → 用户确认接口 → Java 写入 → 状态回查 → 取消 → 回查，以及越权、过期、规则变化、重复/并发确认、超时和服务重启。模拟通过不代表真实 Java/Redis 联调通过。

真实验收由用户在页面核对具体券后确认，不通过脚本盲目订阅。核对现有商户页面的候补状态应与驴友回查一致；若已发券，显示状态2并转到商户页查看，不用“取消候补”冒充取消订单。
